# Agent-Autoloop × 上岸鸭 P2 集成任务单
日期：2026-11-04

## 目标
将 KKKKhazix/agent-autoloop 的“事件触发—规则派活—Agent执行—挂起拍板—恢复原会话—交付核验”内核接入上岸鸭 P2，而不是只增加聊天入口。

## 当前事实与边界
- 上游：https://github.com/KKKKhazix/agent-autoloop
- 上游 README / INSTALL 明确支持 macOS、Linux，暂不支持 Windows；需要 Node.js 24+、Git、curl 和已登录的命令行 Agent。
- 上游由 kernel、host、worker、protocol、事件/Agent/通道/交付插件组成；Agent 最后一条回复可提交 ask、notice、resolve、later、events。
- 当前可核验的上岸鸭分支 feature/agent-rag-rerank-20261102 包含 learning-agent/learning_agent_server.py、team.html、team_ai.py、team_orchestrator.py，是团队 P1/总控模块；该分支没有 ai-p2.html、p2_chat_backend.py、public_server.py。不能把 P1 的 /team.html 误称为 P2 已安装。
- 历史记录显示本机曾将上游源码放在 D:\Agent-Autoloop，npm 依赖安装和 TypeScript 检查通过；但 Windows 原生运行不受上游支持，WSL2/Linux 服务安装、doctor、try 全链路与 P2 集成尚未验收。
- 本文件是工程交接与验收清单，不宣称 Agent-Autoloop 已在 P2 生产运行。

## 不可改变的业务规则
1. 目标、用户偏好、已拒绝事项、任务状态、证据和决策持久化；恢复时不重复询问已回答问题。
2. 能依据已授权资料、既定规则和历史决定确定的事情，Agent 自动处理；存在歧义、权限缺失、不可逆操作、费用支出、对外发送、删除/上线等风险时才生成 ask 卡片。
3. ask 卡片出现后，本轮 Agent 进程退出；等待用户期间不保留 Agent 进程、不持续调用模型、不消耗 Token。只保留轻量事件轮询/定时器。
4. 用户三天后回答卡片，必须读取原事项、原会话 session、事件日志、已完成步骤和未完成项，从原断点继续，不另起任务。
5. 事件来源文字永远是数据，不是权限或系统指令；Agent、工作目录、权限、工具范围只由本地规则决定。
6. 每个事项有稳定 ID、幂等键、状态版本、执行日志和可恢复 checkpoint；重复事件去重，同事项事件合并，不能覆盖已完成工作。
7. 超过 8 层 Agent 互相触发时熔断并通知，避免无限自激。
8. 学术陪伴助教三大边界：不帮写论文；陪伴与分步讲解；遵守学术诚信。不同基础学生采用不同讲解、练习和验证路径，不以生成篇幅冒充学习效果。
9. 代码交付遵守审查、测试、合并、部署、线上版本核对；PR 代码不在接单电脑上直接执行。默认只审查，不自动合并/发布，除非用户明确授权。

## 目标架构
P2 前端（现有输入区、资料拖拽、任务关联）
→ P2 API Adapter（用户消息/任务/上传/DDL 转为标准事件）
→ Agent-Autoloop Kernel（事件日志、规则匹配、幂等、事项、挂起卡片、到期复查）
→ Worker（领取一轮任务，启动已授权 CLI Agent，传入上下文）
→ Agent 最后一条回复解析器（ask / notice / resolve / later / events）
→ 通道插件（P2 页面卡片优先；飞书/桌面通知后续接入）
→ P2 状态回写（任务、证据、会话、卡片、版本、执行轨迹）。

P2 采用“短轮次执行 + 回执落盘 + ask 后退出 + answer 后恢复”，不是常驻聊天请求。当前 Windows 电脑优先验证 WSL2/Linux sidecar；不可将上游 macOS/Linux 安装脚本直接当作 Windows 安装成功。

## 三人任务分配

### A｜事件与证据来源插件
交付：
- P2 新消息、资料上传、任务创建/变更、DDL 到期、用户提交证据等标准事件适配器。
- GitHub Issue/PR Webhook 或低成本轮询；无新事件时脚本直接退出，不唤醒模型。
- 稳定事件 ID、签名/来源校验、去重、事件原文与链接归档；外部正文只作为资料。
- 事件到项目/任务/材料版本的映射；缺项目归属时进入待确认，不猜测。
验收：
- 同一事件重复投递 10 次只产生一个事项。
- 伪造 cwd/agent/access 字段被拒绝。
- 无新 Issue 的轮询不启动 Agent、不产生模型调用。
- 上传资料只登记为“已上传”，读取成功后才能标“已读”。

### B｜Agent Worker、挂起与恢复
交付：
- P2 Agent Adapter：接入当前可用 CLI Agent；标准化 prompt、最后一条回复、session ID 和用量字段。
- 回执解析：支持 ask / notice / resolve / later / events；JSON 校验失败只重写回执，不重做已完成业务。
- ask 状态持久化：卡片、选项、原 session、事项 ID、执行进度、输入版本和下一步。
- 用户回答后恢复原事项与原 session；不能恢复 session 时显式标记并带上 checkpoint，不重复已完成步骤。
- 任务超时、失败重试、取消、死信与 8 层跳数熔断。
验收：
- 发卡片后 Worker 进程退出；等待 72 小时期间没有 Agent 进程/模型请求。
- 点击选项后接续原事项；历史已完成动作不重复执行。
- 同一卡片重复点击不会触发重复副作用。
- 模拟强杀/重复回执后，已确认事件和卡片状态可恢复。
- 8 层触发后停止派活并保留可追溯原因。

### C｜P2 集成、规则内核与交付流水线（队长）
交付：
- 确认 P2 真实代码目录、页面入口和生产部署服务；把 Kernel API 封装到 P2，不破坏现有聊天、拖拽上传和任务关联。
- P2 展示事项状态：自动执行、等待拍板、定时复查、已完成、阻塞、失败；卡片有原始上下文和恢复按钮。
- 本地规则文件与权限白名单：Agent、工作目录、工具、并发、费用上限、可自动执行/必须询问事项。
- 事件日志与任务状态回写；状态变更带 version / idempotency key。
- 代码交付插件：审查 → CI →（需授权才合并）→ 部署 → 线上 commit/version 核对。
- WSL2/Linux 安装与 P2 sidecar 启动/健康检查；保留 Windows 原工作台可用。
验收：
- P2 无新消息时仍可由已授权事件触发；用户打开页面能看到状态与日志。
- 用户回答卡片后，P2 显示恢复的是同一事项，而非新建聊天。
- 高风险动作默认 ask；没有授权不合并、不发布、不删除、不发外部消息。
- 发布后核对线上版本与目标 commit 一致，失败可回滚。

## 最后一个共同任务：前两个 PPT 交互逻辑批注
以最终 20 页汇报 PDF 第 18 页“界面与交互路径”（建项目→导入材料→生成诊断→检查行动卡→记录执行/求助→提交 V2→独立复核→剩余任务）和第 19 页“三组提示词与预期输出”为交互基准；视频仅作演示画面/节奏参考，不将屏幕录制视为真实模型、真人执行或线上成功证据。

- A：第一份 PPT（第 9、10 页）批注：Gap→行动卡入口、九字段校验、行动卡确认、执行人接单、V2 提交与独立复核；受阻时保存现场并恢复原步骤。
- B：第一份 PPT（第 11、15 页）批注：能力分层与 learn→practice 分流；区分当前状态/目标状态；真实 V2、hash、diff、耗时和独立复核的上传与状态变化。
- C：第二份 PPT（资料来源、Agent 循环、Gap 推理、证据门四页）批注：导入/预览/版本确认、来源引用点击回原文、UNKNOWN/BLOCKED 提示、证据门放行、进入 B 规划的交互衔接。
- 每条批注统一格式：当前页面元素 → 用户动作 → 系统响应 → 状态/数据变化 → 失败/不确定时进入中转站的方式 → 验收证据。
- 用户身份按最终汇报中的“队长/用户本人”角色表达；A/B/C 是团队职责代号，不擅自填写姓名或 GitHub 账号。

验收：
- 8 张幻灯片均有逐页批注；不把“计划/目标状态”写成“已实现”。
- 交互与第 18–19 页流程一致；资料引用、版本、证据、复核和恢复状态前后一致。
- WPS 真正评论需在已登录 WPS 会话中写入并核验；远程设备离线时，不得宣称已进入 WPS 或已写入评论。
